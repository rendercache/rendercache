RenderCache 0.1.0-alpha.2 fixes a forwarding bug that could send crawlers into a redirect loop, and tidies up how request-driven pages, tracking parameters and API paths are handled.

**Forwarding headers.** In alpha.1 the origin saw every crawler miss as plain HTTP from the edge's address, because RenderCache rebuilt the X-Forwarded-* headers from its own connection. Apps that force HTTPS from X-Forwarded-Proto redirected crawlers back to the same URL. RenderCache now keeps the X-Forwarded-For chain and a valid X-Forwarded-Proto and X-Forwarded-Host when the request comes from an address in the new `trusted_proxies` setting (loopback by default, which covers the nginx example) or carries the configured edge token. Other callers still can't set these headers. The Cloudflare Worker example now sends the visitor address, scheme and host, and the container config trusts the Docker bridge range. If nginx reaches RenderCache from another host, add that address to `trusted_proxies`.

**Crawler list.** Google-InspectionTool is now in the default list, so Search Console's URL Inspection and Rich Results Test see the cached page. GoogleOther, Amazonbot, YandexBot, Baiduspider and CCBot were added too. The nginx and Worker examples match.

**Request-driven pages.** When all `request_page_limit` slots are used, a new URL now takes the slot of the least recently requested idle page instead of being refused until restart. Pages that are queued, rendering, waiting for a purge or withdrawn keep their slots. An evicted page's snapshot stays on disk and is still served. `/status` reports `request_evictions`.

**New settings.** `ignore_query_params` keeps utm_*, gclid, fbclid and msclkid out of the snapshot identity, so tracking links share one snapshot. `bypass_paths` replaces the fixed `/api` prefix, for apps that also use `/graphql`, `/wp-json` or similar. Existing config files keep working: all three new settings have defaults.

**Caching.** Assets and bypassed paths no longer get `Vary: User-Agent, Cookie`, so a CDN in front can cache them normally.

Linux amd64 binary archive and SHA-256 checksums are attached. Chrome/Chromium is an external dependency for the standalone binary; the Dockerfile installs it. This is an evaluation alpha, not a production-readiness claim. The release pipeline ran race-enabled Go tests with real Chrome, a non-root Chromium container under resource limits, nginx routing, the Cloudflare Worker tests, deterministic archive rebuilds, checksums and the extracted executable. Known limits are unchanged from alpha.1 and listed in the README and deployment guide.
